# 流水线说明

本仓库承载的是一条 AI 辅助软件交付（SDLC）的最小闭环流水线：**需求 → 实现 → 评审 → 合并**。agent 负责实现与自检，评审账号给出正式结论，人负责决策与合并。本文说明这条流水线的入口与分工；账号清单与派活约定的摘要见 [README](../README.md)。

## 入口

新任务从飞书群发起：在群里 `@DSH-SDLC-Bot`，一句话说明目标、范围和验收标准。机器人接住请求后受理、分派给执行 agent。

一条合格的请求应包含：

- **目标**：要做成什么；
- **范围**：涉及哪些文件或目录，以及明确不在本次范围内的事；
- **验收标准**：改完怎么算对——可执行的检查、测试或明确的对照标准。

GitHub 仓库 `allenxu-lego/tapestry-ai-sdlc-poc` 是代码落点：agent 在其 `agent/*` 分支上开 PR，评审与 CI 在 PR 上进行，仓库活动会被流水线跟踪。

## 分工

| 角色 | 谁来做 | 职责 |
| --- | --- | --- |
| 接单 | `DSH-SDLC-Bot`（飞书机器人） | 接住请求，判断是否受理、归到哪个任务，分派给执行 |
| 执行 | `allenxu-lego`（agent 账号） | 领取任务、调研、写代码、推 `agent/*` 分支、开 PR、在 PR 上留评审意见 |
| 评审 | `lunyanxu1981` | 提交正式结论：`APPROVE` 或 `REQUEST_CHANGES` |
| 合并 | 人 | PR 由人合并 |

提交作者署名统一为 `dsh-superagent`（挂在 `allenxu-lego` 账号的 noreply 邮箱下），便于在 git 历史里区分哪些改动来自 agent。执行与评审由两个不同的 GitHub 账号承担，避免 agent 给自己的 PR 批准。

## 流水线阶段

```
需求  →  实现  →  评审  →  合并
```

1. **需求**：人在飞书群发起请求，机器人受理并分派。范围不清或需要设计决策时，agent 会停下并提一个具体问题，而不是替你猜。
2. **实现**：agent 在 `agent/*` 分支上调研、改代码、自检并运行相关检查，然后推送并开 PR。PR 描述写清改动、验证方式与已知限制。
3. **评审**：评审账号在 PR 上提交正式结论。`REQUEST_CHANGES` 时 agent 修完再推；`APPROVE` 后进入待合并。
4. **合并**：由人合并 PR。

## 边界

- agent **不合并 PR**，也**不替他人批准**；合并始终由人决定。
- 需要设计决策时，agent 停下来提一个具体问题，而不是自行扩大范围。
- 涉及密钥、token、内部地址不要提交；本地凭据放 `.local-secrets/`（已被忽略）。
